# 从示例工程积累可执行的 PCB 知识

本项目把示例工程变成三类材料：原始工程的有证据结构模型、只对该板适用的案例观察、具有适用条件的通用设计方法。模型权重保持原样；Codex 通过技能与 MCP 在任务时读取这些材料。

## 每块板的摄入方式

先校验源归档的哈希、CRC、版本和文档结构，按工程/Board/SCH/PCB UUID 隔离文档；解析过程只读取 JSON，不执行文件内脚本或注释。日志用 type/id/ticket 合并历史记录，未支持的删除行为明确报告。无位号图框、网络标志与实际器件分开处理；同号多个物理焊盘全部保留。

再建立功能块、器件/封装/焊盘网络和层/线/过孔/铜区索引。器件位号一致只证明对象身份一致；引脚级网络、实际连通、参考连续性和制造要求还需 EDA/专项工具的证据。器件实例的局部封装覆盖优先于器件库默认值；符号 PART/PIN 只在所属 SYMBOL 内查找，不能跨库用相同 partId 配对。

本机的准确源归档、完整模型和逐板笔记保留在 Git 忽略目录。公共文档仅沉淀方法和公开来源，不把某一板的坐标、线宽、层名或历史 DRC 当作新板默认。

## Codex 查询顺序

1. 用 `pcb_inspect_local_project` 获取 PCB UUID、文档关联、实际启用铜层和对象数量。
2. 用 `pcb_query_board` 按 PCB UUID 和精确位号/网络名查询局部器件、焊盘网络与布线统计；以返回的归档成员、行、ticket 作证。
3. 用 `pcb_case_search` 查本机案例笔记，找已经观察的做法和不能外推的条件。它缺少本地文件时直接报告不可用。
4. 用 `pcb_search` 和 `pcb_sources` 对照官方规则，再按目标器件/工艺补齐参数。案例数值与手册规则冲突时保留差异，优先核实当前器件、版本和工艺。
5. 按 [设计指南](../../docs/field-guide.md) 形成分区、关键回路、机械/层叠/网络约束和验证计划。当前 MCP 只读，没有 EDA 写入、自动布线和 DRC 执行能力。

## 怎样形成设计能力

每条布局/布线建议保存对象、约束来源、适用条件、候选原因、执行结果和验证证据。只有在副本中真实完成写入、读回对比、完整 DRC/网络与制造检查，并达到相应分析或实测要求后，才能把它升级成已验证案例。失败也入库，记录触发条件、原因与修正；不用单一示例当作所有 MCU 的监督真值。

后续 EDA 接入见 [架构](../../docs/architecture.md)，真实验收见 [验证](../concepts/verification.md)。
